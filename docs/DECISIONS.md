# 설계 결정 기록

주요 설계 결정마다 맥락, 고른 방법, 버린 대안, 대가를 남깁니다.

---

## D1. 코드 생성은 결정적 템플릿, LLM은 선택적 고도화

**맥락:** 그래프를 LangGraph 코드로 바꾸는 방법은 두 가지가 있습니다. 하나는 LLM에게 매번 쓰게 하는 것이고, 다른 하나는 템플릿으로 생성하는 것입니다.

**결정:** 기본은 결정적 템플릿 생성기(`codegen/`)입니다. LLM은 사용자가 원할 때만 "고도화"에 쓰고, 검증을 통과해야 결과를 받아들입니다.

**이유**
- 같은 그래프는 항상 같은 코드가 되므로 스냅샷 테스트로 출력을 고정할 수 있습니다.
- 그래프를 고칠 때마다 코드가 즉시 바뀝니다. 지연도 비용도 0입니다.
- 키가 없는 학습자도 쓸 수 있습니다.

**대가:** 템플릿은 노드 종류가 늘어날 때마다 직접 확장해야 합니다. 그래서 생성 결과의 "실행 가능성"을 CI에서 매번 실제로 돌려 보장합니다(패턴 12종).

## D2. LLM 출력은 실행해서 검증한 뒤에만 쓰고, 구조 해시로 캐시

**맥락:** LLM이 고친 코드는 그럴듯해 보여도 실행하면 깨질 수 있습니다.

**결정:** 다음 순서로 처리합니다.
1. ruff로 실행 시 바로 터지는 오류를 검사합니다.
2. Mock LLM 모드로 실제로 실행합니다.
3. 실패하면 오류 보고서를 붙여 최대 3회 다시 요청합니다.
4. 통과한 코드만 그래프 구조 해시로 GCS에 캐시합니다.

**이유:** "LLM을 신뢰하지 않는 파이프라인"입니다. 한 번 통과한 구조는 모든 사용자가 LLM 호출 없이 재사용하므로, 비용이 사용자 수가 아니라 서로 다른 구조의 수에 비례합니다.

**대가:** Mock 실행은 흐름이 끝까지 도는지만 확인합니다. 응답의 품질까지는 검증하지 않습니다.

## D3. 실행 전 정적 분석

**맥락:** 그래프 결함은 런타임에 다음 세 가지 중 하나로 나타납니다.
- 예외로 죽거나
- 무한 루프로 LLM 비용을 태우거나
- **아무 증상 없이 지나갑니다.**

**결정:** 코드를 만들기 전에 브라우저에서 구조를 분석합니다. 오류가 있으면 실행 버튼을 막고, 문제가 있는 노드와 엣지를 빨간색으로 표시합니다.

**근거 (실측, [EVAL.md](EVAL.md)):**
- 결함을 주입한 그래프 97건 중 31건(32%)은 실행해도 오류가 나지 않았습니다. 11건(11%)은 무한 루프였습니다.
- 분석기는 97건을 모두 잡았고, 정상 변경 48건에서 오탐은 0건이었습니다.

**대가:** 규칙 기반이라 의미 수준의 오류(잘못된 프롬프트 등)는 잡지 못합니다.

## D4. 샌드박스: 컨테이너 안의 subprocess + rlimit

**대안**
- Pyodide(브라우저 WASM): LangGraph, chromadb 같은 네이티브 의존성이 무겁고, 네트워크 제약이 있습니다.
- 실행마다 컨테이너나 Firecracker 마이크로VM: 격리는 가장 강하지만, 시작 지연과 운영 비용이 큽니다.
- **subprocess + rlimit + 프로세스 그룹 kill + non-root 컨테이너**

**결정:** 세 번째 방법입니다. 시작이 빠르고(실행 1회 약 2초, 대부분 import 시간), Cloud Run 한 서비스로 운영할 수 있습니다.

**대가:** 커널을 공유하므로 격리 수준이 VM보다 낮습니다. 트래픽이 늘면 gVisor나 Firecracker로 옮겨야 합니다. 그래서 [알려진 한계](../README.md#알려진-한계)에 적어 두었습니다.

## D5. 사용자 API 키는 샌드박스에 넣지 않는다 (키 주입 프록시)

**맥락:** BYOK 구조에서 공유 프로젝트 코드가 `os.environ`에서 키를 읽어 외부로 보낼 수 있었습니다.

**대안**
- 아웃바운드 네트워크를 `api.openai.com`만 허용하는 방화벽: Cloud Run에서 도메인 단위로 이그레스를 제한하려면 VPC와 프록시가 필요해서 무겁습니다. 게다가 허용된 OpenAI로 키를 보내는 우회는 여전히 가능합니다.
- 공유 프로젝트 실행 금지: 공유 기능의 가치가 사라집니다.
- **샌드박스에는 가짜 키를 주고, 같은 워커에 띄운 로컬 프록시가 진짜 키를 붙여 허용된 엔드포인트로만 전달**

**결정:** 세 번째 방법입니다. 실행별 토큰은 실행이 끝나면 폐기합니다. 비용 남용은 두 가지로 줄입니다.
- 설정 창에서 사용 한도를 건 전용 키를 쓰라고 안내합니다.
- 작성자가 쓴 코드가 있는 공유 프로젝트는 실행 전에 확인 창을 띄웁니다(Mock 실행 선택 가능).

**대가:** 실행 중인 코드가 그 키로 허용된 API를 호출하는 것까지는 막지 못합니다.

## D6. 트레이스는 LangChain 전역 콜백 + 별도 파이프

**대안**
- 생성 코드에 로깅을 넣는 방법: 강의 코드처럼 사용자가 직접 쓴 코드에는 적용할 수 없습니다.
- stdout에 표식을 붙여 섞는 방법: 사용자 출력과 충돌하고, 파싱이 깨지기 쉽습니다.
- LangSmith: 외부 서비스 계정이 필요하고, 사용자 데이터가 제3자에게 갑니다.

**결정:** `sitecustomize.py`가 LangChain 전역 configure hook에 트레이서를 등록하고, 이벤트는 전용 파이프(fd)로 보냅니다.

**이유:** 강의 코드, 플레이그라운드 코드, 사용자가 붙여 넣은 코드 모두 수정 없이 동작합니다. stdout은 사용자의 것으로 남습니다.

**대가:** LangChain/LangGraph를 거치지 않는 호출(OpenAI SDK 직접 호출 등)은 보이지 않습니다.

## D7. 프론트와 백엔드를 fixture로 잇는 통합 테스트

**맥락:** 코드 생성은 TypeScript이고 실행은 Python입니다. 생성기가 바뀌었을 때 생성 코드가 여전히 실행되는지 확인할 방법이 필요했습니다.

**결정:** 생성 결과를 `backend/tests/fixtures/patterns.json`으로 내보내고, 두 쪽에서 각각 검사합니다.
- vitest: fixture가 현재 생성기 출력과 같은지
- pytest: fixture를 샌드박스에서 실행했을 때 모두 성공하는지

**이유:** 언어 경계를 넘는 회귀를 CI에서 잡고, 두 테스트 스위트를 각자 빠르게 유지합니다.

## D8. 한도는 메모리에, 비용 상한은 인프라에

**결정:** 분당·하루 한도는 인스턴스 메모리에 기록합니다. 대신 Cloud Run 최대 인스턴스를 1로 둬서 전체 비용 상한을 인프라가 보장하게 합니다.

**이유:** 개인 프로젝트 규모에서는 Redis 같은 외부 저장소를 둘 이유가 비용 대비 작습니다.

**대가:** 인스턴스가 늘어나거나 재시작되면 실제 허용량이 커질 수 있습니다. 규모가 커지면 Supabase 테이블이나 Redis로 옮겨야 합니다.
